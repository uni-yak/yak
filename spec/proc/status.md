# status

## 元信息

- 名称：status（规格状态、实现态与冻结门禁）
- 级别：流程
- 状态：确认
- 依赖：`../index.md`、`gate.md`、`error.md`

## 一、状态值

规格状态按约束强度从高到低为：确认、草案-可实施、草案、缺失。

| 状态 | 含义 | 实现权限 |
|:---|:---|:---|
| 确认 | 主管规格、直接依赖、拒绝形态、错误码与验证门禁已冻结 | `yakc-min` / `yakc-full` 可依赖，产物进入正式门禁与发布 |
| 草案-可实施 | 主管规格已封闭合法形态、默认行为、状态转换与拒绝形态；错误码已登记；正负例资产已登记；跨规格审计、目标 ABI / 布局验证与固定点门禁尚未完成 | 仅 `yakc-min` 可在 seed 下参考实现并进入快速门禁回归；产物只登记为参考态，不进入正式发布与固定点门禁；`yakc-full` 不得实现 |
| 草案 | 已记录候选合同，但仍待跨规格审计、实现设计或验证门禁 | 不得作为已实现能力；源码出现时失败关闭，除非主管规格明示为可解析保留形态 |
| 缺失 | 尚无主管规格或主管规格为空 | 不得解析、脱糖、检查、降级、发射或文档化为语言能力 |

1.1 「草案-可实施」是草案的可实施子态，不授予冻结语义：其合法形态若在跨规格审计或真机验证中发现矛盾，可修订规格并同步错误码与测试，不触发「已确认规格变更」门禁。

1.2 规格状态是全局属性；编译器的实现态由 `../index.md` 的矩阵逐编译器登记，两者不得混用。

## 二、状态迁移条件

2.1 规格从「草案」进入「草案-可实施」，必须同时满足：

- 主管规格列出全部合法形态、默认行为、状态转换与拒绝形态，边界封闭，无悬空的待定分支；
- 每个诊断拒绝形态在 `error.def` 中登记唯一 `ErrorCode` 或显式复用已有码位。流程门禁断言按主管规格登记失败条件和门禁结果；源码无触发形态的静态断言登记其前置拒绝条件；
- 每个合法形态与可书写的拒绝形态至少登记一个用例。种子解释器回归位于 `seed/test/`，编译器语料位于 `test/ok/` 与 `test/bad/`，跨阶段或不可由源码直接触发的断言可登记到 `test/gate/` 或 `test/unit/`；
- 依赖规格的状态不低于「草案-可实施」，或主管规格显式列出并封闭其仍为草案的边界。

2.2 规格从「草案-可实施」进入「确认」，必须同时满足：

- 类型、语法、名字、所有权、布局、ABI、错误码与测试门禁均有唯一主管规格；
- 上游依赖均为确认，或主管规格明确列出并封闭其仍为草案的边界；
- 所有合法形态、默认行为、状态转换、拒绝形态与诊断归属已定义；
- 同一语义不存在两个并列真源；
- 已登记对应正例、负例和风险相关的目标验证，且完整门禁（`gate.md` 2.2）通过。

评审使用隔离的待确认快照。拟确认的规格、对应实现登记与待验收源码须属于同一快照，并在该快照内重新生成和验证产物。评审通过后才一并登记正式规格状态与实现态，验收记录按 `gate.md` 2.4 归档。

2.3 草案不得因解析器、示例、注释、历史实现或参考项目中存在类似形态而自动升级为「草案-可实施」或「确认」。

2.4 已确认规格不因新增草案或草案-可实施规格静默改变。下级态规格必须写明不改变的现行真源、依赖、实现前置条件和冻结门槛。

## 三、实现门禁

3.1 `yakc-min` 只可为实现态登记为「契约态」或「参考态」的规格产出目标代码；「契约态」要求规格为确认，「参考态」要求规格为草案-可实施。`yakc-full` 只可实现确认规格。

3.2 「参考态」产物可按 `fixpoint.md` 的候选取证规则在隔离目录试运行自编译链。正式评审使用 2.2 规定的待确认快照重新生成产物，按完整门禁核验。候选结果的效力限于其实际验证范围。

3.3 参考态之外的草案形态，除主管规格明确允许的解析保留外，一律产生已登记诊断。解析保留不等于类型检查、MIR、布局、ABI 或代码生成支持；任一后续阶段缺少完整合同必须失败关闭。

3.4 新增或改写语言、接口、ABI、格式、公共 API 的草案时，必须同步更新 `../index.md`、关联类型规格、错误码数据与验证门禁。
